# US-023. Display IPA in the `ipa-lookup` CLI subcommand

Part of [FEAT-002](FEAT-002.md) (split for parallel implementation — see that
feature for the full background). **Depends on [US-019](US-019.md), [US-020](US-020.md),
[US-021](US-021.md), and [US-022](US-022.md) all landing first** — it converts the raw
tokens [US-019](US-019.md)'s loader returns back to IPA using [US-020](US-020.md)'s
`ga-tokens->ipa` and [US-021](US-021.md)'s `rp-tokens->ipa`, and it edits the same
`core.clj` `ipa-lookup` subcommand [US-022](US-022.md) already touches, so it
lands after to avoid conflicting edits.

As a user of the `ipa-lookup` CLI subcommand, I want to keep seeing IPA
output for a word's GA/RP pronunciation, so that the switch to raw-token
storage ([0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md)) is invisible
at the CLI — the subcommand still shows `/kɑːr/`-style IPA, not raw
`K AA1 R` tokens, even though the underlying dictionary and matching now
operate on tokens.

## background
Once [US-019](US-019.md) renames `load-rp-ga-dict` to `load-ga-rp-dict` and
changes its row shape to `{:word :ga-tokens :rp-tokens}`, and [US-022](US-022.md)
migrates matching to token space, `ipa-lookup`'s output would otherwise
regress from displaying IPA to displaying raw ARPABET/MRPA tokens. This
story is the display-side fix: nothing breaks without it (unlike
[US-022](US-022.md)), but the CLI's user-facing output quality regresses until it
ships.

## Protocol
- `core.clj`'s `ipa-lookup` subcommand converts each looked-up row's
  `:ga-tokens` through [US-020](US-020.md)'s `ga-tokens->ipa` and `:rp-tokens`
  through [US-021](US-021.md)'s `rp-tokens->ipa` before printing, instead of
  printing the raw token fields directly.
- Multi-variant cells (comma-joined token strings) convert to
  comma-joined IPA, same convention `ga-tokens->ipa`/`rp-tokens->ipa`
  already handle per their own stories.
- No change to `lookup-rows`/`word-matches?` internals ([US-022](US-022.md)'s
  territory) — this story only touches the CLI's presentation of
  already-fetched rows.

## Acceptance Criteria

```gherkin
Scenario: ipa-lookup prints IPA, not raw tokens, for a GA column
  Given a dict row {:word "car" :ga-tokens "K AA1 R" :rp-tokens "k aa"}
  When the ipa-lookup subcommand looks up "car"
  Then the printed GA output is IPA (e.g. "/kˈɑɹ/"), not the raw string "K AA1 R"

Scenario: ipa-lookup prints IPA for an RP column
  Given a dict row {:word "car" :ga-tokens "K AA1 R" :rp-tokens "k aa"}
  When the ipa-lookup subcommand looks up "car"
  Then the printed RP output is IPA, not the raw string "k aa"

Scenario: comma-joined multi-variant token cells print as comma-joined IPA
  Given a dict row with :ga-tokens "R IY1 D,R EH1 D"
  When the ipa-lookup subcommand looks up that word
  Then the printed GA output shows both variants as comma-joined IPA

Scenario: an absent column still prints as empty, not an encoding error
  Given a dict row with :rp-tokens ""
  When the ipa-lookup subcommand looks up that word
  Then the printed RP output is empty, with no conversion error raised
```

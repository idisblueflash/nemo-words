# US-012. Filter out onset-r false positives from rhotic lexical-set lookups

As an engineer building the rhotic Lexical Sets (NURSE, NEAR, SQUARE, START, NORTH, FORCE, CURE — the seven of Wells' 24 sets whose defining sound ends in `r`), I want a narrow post-filter on [[US-001]]'s substring matches, so that a word like "oware" doesn't get counted as a START example just because its raw IPA happens to contain "ɑɹ".

## Background

Grooming the `gnarly` mnemonic card (`nemo-english/cases/gnarly.md`) surfaced that [[US-001]]'s substring lookup (`{:ga "/ɑɹ/"}` etc.) over-matches for the seven rhotic sets. The `r` in a Wells rhotic set's defining sound only counts when it's in the **coda** of the syllable containing the stressed vowel (a genuine r-colored/rhotic vowel, e.g. "car", "arcan"). When that same character sequence appears because `r` is the **onset** of the *next* syllable (a linking/intrusive `r` before a following vowel, e.g. "oware", "amaro"), it isn't the same sound and shouldn't count — but a plain substring match can't tell the two apart, because Kaikki's transcriptions don't reliably mark syllable boundaries.

Checked against the real `en_US_RP_ipa.tsv` (see [[US-001]] for its corrected `word\tGA-cell\tRP-cell` shape):

```
False positives (r is onset of the following syllable — do NOT belong in the set):
  oware      /əˈwɑɹi/        "wa-re", not START
  amaro      /əˈmɑɹoʊ/       "ma-ro", not START
  dieri      /ˈdɪəɹiː/       "die-ri", not NEAR
  echeveria  /ˌɛkɨˈvɪəɹiə/   "ve-ri-a", not NEAR
  adjarian   /əˈd͡ʒɑɹi.ən/    "ja-ri-an", not START (confirmed against en_US_RP_ipa.tsv)

True positives (r closes the syllable — belong in the set):
  car        /kɑɹ/           word-final r, unambiguous (confirmed against en_US_RP_ipa.tsv)
  arcan      /ˈɑɹ.kæn/       r before a consonant (Kaikki even marks the dot here)
  starry     /ˈstɑɹ.i/       r before a dot then a vowel-only syllable — still coda
  fireport   /ˈfaɪəɹˌpɔɹt/   r before a stress mark then a consonant — still coda
```

Kaikki's GA transcriptions use narrow IPA for r-colored vowels — the vowel followed directly by `ɹ`, no length mark (see [[FEAT-001]] background) — so all the sounds and fixtures above and in the ACs below use `ɑɹ`/`aɪəɹ`/etc., never the Cambridge-style `ɑːr` form. `car` and `adjarian` are checked against the real `en_US_RP_ipa.tsv`; the rest of this table is illustrative.

This is a structural pattern (single consonant flanked by vowels always resyllabifies as the next syllable's onset — the one case where the Maximal Onset Principle has no ambiguity to resolve), not a one-word quirk: it recurs across all seven rhotic sets, since they all define their sound by a vowel + coda `r`.

**Why not build a full syllabifier (Sonority Sequencing Principle + Maximal Onset Principle)?** Considered and rejected for now:
- Every false positive found is the *unambiguous* single-intervocalic-consonant case. MOP's answer for that case is fixed by convention (resyllabify as the next onset) and needs no sonority hierarchy or English onset-cluster legality table — the machinery a general syllabifier needs. No genuine cluster-boundary ambiguity (the case that *would* need that machinery) turned up in the rhotic sets.
- Kaikki's own syllable-boundary dots (`.`) are sparse and inconsistent (most entries have none — e.g. `alipurduar\t/əlipʊəɹduˈɑːr/`), so there's no reliable ground truth to validate a general syllabifier's output against.
- The other 17 (non-rhotic) Wells sets don't need this at all: happY vs. KIT looked like a symbol clash (`/ɪ/` for both) but Kaikki already resolves it lexically (`copy /ˈkɑpi/ /ˈkɒpi/` uses tense `/i/` for happY, not `/ɪ/`); CLOTH vs. LOT vs. THOUGHT is a genuine GA merger with no phonetic distinction left in the data at all (`cloth` has an empty GA cell) — that's a curated-wordlist problem for [[US-006]]/[[US-007]]/[[US-009]], not something any syllabifier could recover.

So the fix is scoped to exactly what's broken: a local lookahead rule, applied only when building the seven rhotic sets.

## Protocol

`nemo-words.rime/coda-match?` — pure function `[ipa-string sound] -> boolean`. True iff `sound` occurs in `ipa-string` at a position not immediately followed by a vowel character, skipping over any stress marks (`ˈ`/`ˌ`) or syllable dots (`.`) between the match and the next character. A cell may contain comma-joined variants (per [[US-001]]'s data-reality note); the row counts if *any* occurrence in the raw string is coda-position, mirroring how [[US-001]]'s substring match already treats multi-variant cells.

`nemo-words.rime/filter-coda` — `[rows ipa-key sound] -> rows`, filters a [[US-001]] `lookup-rows` result down to rows where `(coda-match? (ipa-key row) sound)` is true. [[US-004]] and [[US-006]] call this immediately after `lookup-rows` when (and only when) building one of the seven rhotic sets — non-rhotic sets skip it entirely.

## Acceptance Criteria

```gherkin
Scenario: Word-final r is always coda
  Given the IPA string "/kɑɹ/" and sound "ɑɹ"
  When coda-match? is called
  Then it returns true

Scenario: r before a consonant is coda
  Given the IPA string "/ˈɑɹ.kæn/" and sound "ɑɹ"
  When coda-match? is called
  Then it returns true

Scenario: r before a stress mark then a consonant is still coda
  Given the IPA string "/ˈfaɪəɹˌpɔɹt/" and sound "aɪəɹ"
  When coda-match? is called
  Then it returns true

Scenario: r immediately before a vowel is onset, not coda
  Given the IPA string "/əˈwɑɹi/" and sound "ɑɹ"
  When coda-match? is called
  Then it returns false

Scenario: r before a dot then a vowel-only syllable is still coda
  Given the IPA string "/ˈstɑɹ.i/" and sound "ɑɹ"
  When coda-match? is called
  Then it returns true

Scenario: multi-variant cell counts if any variant is coda-position
  Given the IPA string "/əˈvɑɹi/, /kɑɹ/" and sound "ɑɹ"
  When coda-match? is called
  Then it returns true, because the second variant is coda-position even though the first is not

Scenario: sound absent
  Given an IPA string that does not contain sound at all
  When coda-match? is called
  Then it returns false

Scenario: filter-coda drops onset-r false positives from a lookup-rows result
  Given rows for "car", "arcan", "oware", and "amaro" all returned by a GA substring lookup for "ɑɹ"
  When filter-coda is applied with ipa-key :ga and sound "ɑɹ"
  Then the result contains "car" and "arcan"
  And the result does not contain "oware" or "amaro"

Scenario: non-rhotic sets never call filter-coda
  Given [[US-004]] is building a non-rhotic set (e.g. KIT)
  Then filter-coda is not invoked in that pipeline
```

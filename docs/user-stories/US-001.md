# US-001. Support IPA search for both RP and GA
As an engineer, I want to have a CLI so that I can search word with phonetic symbol.

## background
I export the word, GA IPA, and RP IPA as a en_US_RP_ipa.tsv file (2.5 MB) from the original huge one, then I can build a CLI based on it.

Here's the command we run to download the original dict (.jsonl 3.2GB).
```bash
aria2c -c -x4 -s4 --file-allocation=none \
  -o resources/data/kaikki-en.jsonl \
  https://kaikki.org/dictionary/English/kaikki.org-dictionary-English.jsonl
```

## Data reality (checked against the actual file, 62,894 rows)
`en_US_RP_ipa.tsv` is `word\tGA-cell\tRP-cell` — **GA first, then RP** (confirmed against `scripts/build-kaikki-ipa-dict.js`'s own header comment, `word<TAB>GenAm-IPA<TAB>RP-IPA`, and cross-checked against real rows, e.g. `car\t/kɑɹ/\t/kɑː/`: column 1 is the rhotic GA form, column 2 the non-rhotic RP form). An earlier draft of this doc had the two columns swapped — fixed here before any code reads the file, since `lookup-rows` doesn't exist yet. The RP/GA cells are **not** clean single transcriptions:
- 14,577 rows (~23%) have an **empty RP cell** (e.g. `a-alike\t/ˈeɪəˈlaɪk/\t` — GA present, RP absent) — no RP transcription exists for that word at all. (GA is empty far less often: 2,165 rows.)
- 1,160 rows have **multiple comma-separated GA variants** and 811 rows have multiple RP variants in one cell (e.g. `a\t/eɪ̯/, /ə/, /ˈʌ/\t/eɪ̯/, /ə/, /ʌ/, /ɔ/, /ˈʌ/` — GA cell first, RP cell second), and RP/GA variants are **not positionally paired** — there's no reliable way to know which GA variant goes with which RP variant.

Design decision to resolve this: `lookup-rows` does **not** explode or pair variants. Each output row's `:rp`/`:ga` is the raw cell text exactly as stored — a single string, comma-joined when the source has multiple variants, `""` (not `nil`) when a cell is empty. Substring opts (`{:rp ipa}` / `{:ga ipa}`) test containment against that raw string, so a query matching any one variant inside a multi-variant cell still matches the row. Callers needing one disambiguated variant (e.g. [[US-007]]'s `dominant-pair`) must pick it themselves from a row's raw text — `lookup-rows` won't do it for them.

## Protocol
Core logic lives in `nemo-words.ipa/lookup-rows` — a pure function `[dict opts] -> seq of {:word :rp :ga}`, unit-tested directly on in-memory dict fixtures. `opts` is one of `{:word w}` (exact), `{:rp ipa}` / `{:ga ipa}` (substring), `{:pair [rp ga]}` (exact both — [[US-006]]'s `extend-set` uses this after ranking, once a specific word's own full cells are already known), or `{:pair-substring [rp ga]}` (substring both — both `rp` and `ga` must independently appear as substrings of the row's raw `:rp`/`:ga` text; used by `extend-set` right after [[US-007]]'s `dominant-pair` returns a bare *nucleus* fragment like `"ɑː"` rather than a full cell, so exact `:pair` equality would never match). For `:pair`, "exact" means exact string equality against the row's raw (possibly comma-joined) `:rp`/`:ga` text, per the data-reality note above — not equality against one variant among several.

`core.clj` exposes it as the `ipa-lookup` subcommand (thin: parse args → `lookup-rows` → print TSV `word\tRP\tGA`) because [[US-005]]'s external AI-agent consumer needs a real process boundary.

## Acceptance Criteria

```gherkin
Scenario: Exact word lookup
  Given the dictionary contains the word "car"
  When I look up "car" by word
  Then I get exactly one row: {:word "car" :rp <RP-IPA> :ga <GA-IPA>}

Scenario: Substring match on RP
  Given the dictionary contains words with RP IPA "/ɑː/" as part of their transcription
  When I look up RP substring "/ɑː/"
  Then every returned row's :rp contains "/ɑː/"
  And no row is returned whose :rp does not contain it

Scenario: Substring match on GA
  Given the dictionary contains words with GA IPA "/ɑɹ/" as part of their transcription
  When I look up GA substring "/ɑɹ/"
  Then every returned row's :ga contains "/ɑɹ/"

Scenario: Exact pair match
  Given the dictionary contains words whose RP is "/ˈnɑː.li/" and GA is "/ˈnɑɹ.li/"
  When I look up the exact pair ["/ˈnɑː.li/" "/ˈnɑɹ.li/"]
  Then every returned row has :rp = "/ˈnɑː.li/" and :ga = "/ˈnɑɹ.li/"

Scenario: Substring pair match on nucleus fragments
  Given the dictionary contains "gnarly" with RP "/ˈnɑː.li/" and GA "/ˈnɑɹ.li/"
  And the dictionary contains "narwhal" with RP "/ˈnɑː.li/, /ˈnɑːw.əl/" and GA "/ˈnɑɹ.wəl/, /ˈnɑɹ.li/"
  When I look up the substring pair {:pair-substring ["ɑː" "ɑɹ"]}
  Then both "gnarly" and "narwhal" are returned, since each row's raw :rp and :ga cells independently contain "ɑː" and "ɑɹ" somewhere, even split across different comma-joined variants

Scenario: No matches
  Given the dictionary does not contain the queried word or IPA
  When I perform the lookup
  Then the result is an empty sequence
  And no error is raised

Scenario: Word has no RP transcription
  Given the dictionary contains a word whose RP cell is empty (e.g. "a-alike", GA /ˈeɪəˈlaɪk/, RP absent)
  When I look up that word by :word
  Then the returned row has :rp = "" (not nil)
  And that row is never returned by a :rp substring lookup with a non-empty query

Scenario: Word has no GA transcription
  Given the dictionary contains a word whose GA cell is empty
  When I look up that word by :word
  Then the returned row has :ga = "" (not nil)
  And that row is never returned by a :ga substring lookup with a non-empty query

Scenario: Cell has multiple comma-separated variants
  Given the dictionary contains a word whose GA cell is "/eɪ̯/, /ə/, /ˈʌ/"
  When I look up GA substring "/ˈʌ/"
  Then the row for that word is returned
  And its :ga is the full raw cell "/eɪ̯/, /ə/, /ˈʌ/", not just the matched variant

Scenario: CLI wrapper mirrors the function
  Given the `ipa-lookup` subcommand is invoked with the same query
  When lookup-rows would return N rows
  Then stdout contains exactly N TSV lines "word\tRP\tGA"
  And the process exits 0, even for zero matches
```

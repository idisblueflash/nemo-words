# US-021. Bidirectional MRPA ↔ IPA conversion

Part of [FEAT-002](FEAT-002.md) (split for parallel implementation — see that
feature for the full background). Independent of [US-017](US-017.md)/[US-018](US-018.md)/
[US-019](US-019.md)/[US-020](US-020.md) — pure conversion functions, no file I/O, no brand
parsing. Can be built in parallel with all of them.

As an engineer, I want a `mrpa-phoneme->ipa` map plus forward `mrpa->ipa`
and reverse `ipa->mrpa` conversion functions, so [US-019](US-019.md)'s display
path has RP tokens→IPA, and a future consumer (e.g. translating the
Lexical Sets Table's IPA-authored RP targets into MRPA nucleus tokens, so
nucleus matching can stay token-to-token per
[0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md) instead of decomposing
IPA per word) has IPA→tokens too.

## background
BEEP uses a non-rhotic, lowercase, MRPA-style phoneme inventory, distinct
from CMUdict's ARPABET (see [US-018](US-018.md) for the full inventory listing).
Unlike [US-020](US-020.md)'s ARPABET↔IPA work, neither direction of MRPA↔IPA
conversion exists anywhere in the codebase yet — this is wholly new, not
a reuse-plus-extend of something already shipped.

The forward direction (`mrpa->ipa`) is simpler than ARPABET's: BEEP
tokens carry no stress digit at all (confirmed: zero digit characters
anywhere in `resources/data/beep_uk.dict`'s phoneme fields), so there's
no stress-mark placement logic to write — just a straight per-token map
lookup and concatenation. The reverse direction (`ipa->mrpa`) has the
same multi-codepoint tokenizing challenge [US-020](US-020.md)'s `ipa->arpabet`
has (IPA is a continuous string; `tʃ`, `ɛə`, `ɪə`, `əʊ`, `ʊə` are
multi-codepoint symbols that must be matched greedily/longest-first
against `mrpa-phoneme->ipa`'s values), but with no stress mark to
re-attach.

**Known limitation, accepted**: `ipa->mrpa` is a best-effort
reconstruction, not guaranteed round-trip-exact for arbitrary externally-
authored IPA — only for strings consistent with `mrpa->ipa`'s own output
conventions, same caveat [US-020](US-020.md) accepts for `ipa->arpabet`.

This story is independent of [US-018](US-018.md)'s `:beep-raw` brand-parsing work
— it owns the `mrpa-phoneme->ipa` map itself (moved here from the
original single-story draft, since the map is conversion data, not
parsing logic) and can be implemented/tested with hand-written phoneme
strings, no dependency on `resources/data/beep_uk.dict` being parsed by
anything.

## Protocol
- `mrpa-phoneme->ipa`: BEEP's non-rhotic phoneme map — `{"aa" "ɑː" "ae"
  "æ" "ah" "ʌ" "ao" "ɒ" "ax" "ə" "ay" "aɪ" "b" "b" "ch" "tʃ" "d" "d" "dh"
  "ð" "ea" "ɛə" "eh" "ɛ" "er" "ɜː" "ey" "eɪ" "f" "f" "g" "ɡ" "hh" "h" "ia"
  "ɪə" "ih" "ɪ" "iy" "iː" "jh" "dʒ" "k" "k" "l" "l" "m" "m" "n" "n" "ng"
  "ŋ" "oh" "əʊ" "ow" "aʊ" "oy" "ɔɪ" "p" "p" "r" "ɹ" "s" "s" "sh" "ʃ" "sil"
  "" "t" "t" "th" "θ" "ua" "ʊə" "uh" "ʊ" "uw" "uː" "v" "v" "w" "w" "y" "j"
  "z" "z" "zh" "ʒ"}` (exact IPA choices to be verified against a handful
  of known-good BEEP entries during implementation, same spot-check
  approach US-001's background used for Kaikki's `/ɑɹ/` vs `/ɑːr/`
  question — `ao` in particular needs checking against real LOT-set
  words since BEEP is RP so LOT should map to `ɒ`, not GA's `ɑ`).
- `mrpa->ipa` [MRPA-token-vector → IPA-string]: map each token through
  `mrpa-phoneme->ipa` and concatenate — no stress logic needed (BEEP has
  none).
- `rp-tokens->ipa` [cell-string → IPA-string]: split a raw RP cell on
  `,` (multi-variant), split each variant on whitespace into MRPA tokens,
  run each through `mrpa->ipa`, rejoin variants with `,`. This is the
  function [US-019](US-019.md)'s display path calls.
- `ipa->mrpa` [IPA-string → MRPA-token-vector]: tokenize the IPA string
  greedily against `mrpa-phoneme->ipa`'s value set (longest match first,
  so e.g. `ɛə` is matched as one token, not split into `ɛ` + a stray
  `ə`), no stress mark to strip.

## Acceptance Criteria

```gherkin
Scenario: mrpa->ipa converts a simple token vector
  Given the MRPA token vector ["k" "aa"]
  When mrpa->ipa is called on it
  Then the result is "kɑː"

Scenario: rp-tokens->ipa wraps mrpa->ipa for a single variant
  Given the raw RP cell "k aa"
  When rp-tokens->ipa is called on it
  Then the result is "kɑː"

Scenario: rp-tokens->ipa handles comma-joined multi-variant cells
  Given the raw RP cell "k ea,k eh"
  When rp-tokens->ipa is called on it
  Then the result is "kɛə,kɛ"

Scenario: mrpa->ipa never introduces a stress mark
  Given any MRPA token vector
  When mrpa->ipa is called on it
  Then the result contains no "ˈ" or "ˌ" character

Scenario: ipa->mrpa reconstructs a simple word's tokens
  Given the IPA string "kɑː"
  When ipa->mrpa is called on it
  Then the result is ["k" "aa"]

Scenario: ipa->mrpa handles multi-codepoint IPA symbols
  Given the IPA string "kɛə"
  When ipa->mrpa is called on it
  Then the result is ["k" "ea"], not a mis-split single-character read of "k" "e" "ə"

Scenario: round-trip consistency for mrpa->ipa's own output
  Given any MRPA token vector v
  When v is converted via mrpa->ipa then the result is converted back via ipa->mrpa
  Then the round-tripped token vector equals v
```

## Follow-up
`ipa->mrpa` has no consumer wired up yet — it exists for a future story
(translating the Lexical Sets Table's IPA targets into MRPA nucleus
tokens for [0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md)-style
matching), tracked separately once that need is concretely scoped.

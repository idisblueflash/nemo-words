# US-025. Publish the CLI as a downloadable GitHub Release

Package `nemo-words.core`'s CLI (`word-freq`, `ipa-lookup`,
`pick-example-words-by-ipa`, `build-set`, `populate-lexical-sets`,
`build-ga-rp-dict`) as a single self-contained artifact and publish it as
a GitHub Release, so a user can download and run it from their terminal
without cloning the repo or installing the Clojure CLI — only a JVM.

## Background
Today the only way to run `nemo-words` is `clojure -M -m nemo-words.core
<subcommand>` from a full source checkout with `deps.edn` resolved. There
is no build tooling in the repo at all (no `build.clj`, no `:build`
alias) and no release process.

The CLI's actual runtime resource dependency (per `ipa/load-ga-rp-dict`
and `sets/load!`/`save!`, both reached from `core.clj`'s `-main` dispatch)
is just two files: `resources/data/ga_rp.tsv` and
`resources/lexical-sets.edn` (`build-ga-rp-dict` additionally reads
`cmudict.dict`/`beep_uk.dict` to *regenerate* `ga_rp.tsv`, so those two
raw dicts are kept too). Two other files under `resources/data/` are not
runtime dependencies at all and must not ship:

- `kaikki-en.jsonl` — a ~3GB raw scrape, already `.gitignore`'d, but
  physically present in a dev checkout that has run the original data
  pipeline. Nothing under `src/` reads it.
- `wikipron_uk_broad.tsv` — unreferenced anywhere in `src/` (grep
  confirmed no match); a dead build input.

A first build attempt using `tools.build`'s `copy-dir` (which copies from
disk, not from git) swept `kaikki-en.jsonl` straight into the uberjar,
producing a 474MB artifact — confirming these two files need an explicit
exclude list in the build script, not just reliance on `.gitignore`.

The other CLI entry point in the repo, `nemo-words.ipa`'s own `-main`
(invoked via `clj -M:ipa`, reading `en_US.txt`/`en_UK.txt`/
`wikipron_us_broad.tsv`/`cmudict.dict`), is a separate, undocumented (not
listed in the README's "Other CLI subcommands") dev entry point — out of
scope for this story, which packages only `nemo-words.core`'s documented
subcommands.

Packaging also surfaced a real bug, not just a build-config detail:
`nemo-words.sets/load!`/`save!` used a literal disk-relative path
(`"resources/lexical-sets.edn"`), never the classpath. That's harmless
when running from a source checkout (disk path and classpath happen to
coincide), but inside a jar there is no such disk file, so even the
**read-only** `pick-example-words-by-ipa` subcommand failed from a
packaged jar in any working directory. Fixed by having `sets/load!`'s
default (0-arg) call fall back to the classpath resource
(`lexical-sets.edn`, bundled at the jar root) when no disk override
exists; `core.clj`'s `pick-example-words-by-ipa-cli` now calls the 0-arg
form instead of always passing `sets/default-path` explicitly. Explicit
paths (used by tests and `build-set`/`populate-lexical-sets`, which
*write*) are untouched — a build-set style write into a read-only jar
is a fundamentally different problem, out of scope here (see Follow-up).

## Protocol
- Add `build.clj` (`clojure -T:build uberjar`) using `tools.build`:
  compiles `nemo-words.core`, bundles `src` + `resources` (excluding
  `data/kaikki-en.jsonl` and `data/wikipron_uk_broad.tsv` via an explicit
  `excluded-resources` set), and produces `target/nemo-words.jar` with
  `Main-Class: nemo_words.core`.
- Add a `:build` alias to `deps.edn` depending on `io.github.clojure/tools.build`
  with `:ns-default build`.
- Verify the built jar runs standalone (`java -jar target/nemo-words.jar
  <subcommand>`) matching `clojure -M -m nemo-words.core <subcommand>`
  output, from outside the source tree (no `deps.edn`/`src` on the
  classpath other than what's inside the jar).
- Tag a release (e.g. `v0.1.0`) and publish it with `gh release create`,
  attaching `target/nemo-words.jar` as a release asset.
- Document the download-and-run flow in `README.md` (a "Download a
  release" section: fetch the jar from the GitHub Releases page, run with
  `java -jar nemo-words.jar <subcommand>`, JVM prerequisite noted).

## Acceptance Criteria

```gherkin
Scenario: uberjar excludes non-runtime data files
  Given a dev checkout with resources/data/kaikki-en.jsonl present on disk
    (gitignored, not tracked by git) and resources/data/wikipron_uk_broad.tsv
    tracked but unreferenced by any src/ namespace
  When `clojure -T:build uberjar` runs
  Then target/nemo-words.jar does not contain data/kaikki-en.jsonl or
    data/wikipron_uk_broad.tsv
  And target/nemo-words.jar does contain data/ga_rp.tsv,
    resources/lexical-sets.edn (as lexical-sets.edn), data/cmudict.dict,
    and data/beep_uk.dict

Scenario: the built jar runs standalone with no source checkout on the classpath
  Given target/nemo-words.jar built by `clojure -T:build uberjar`
  When run as `java -jar target/nemo-words.jar ipa-lookup --word car` from
    a directory containing no deps.edn/src/resources
  Then it prints the same "car\t/kɑː/\t/kɑɹ/"-shaped TSV row that
    `clojure -M -m nemo-words.core ipa-lookup --word car` prints from the
    source checkout, and exits 0

Scenario: pick-example-words-by-ipa reads the bundled lexical-sets.edn from the jar
  Given target/nemo-words.jar (built after the sets/load! classpath-fallback fix)
  When run as `java -jar target/nemo-words.jar pick-example-words-by-ipa "ɜɹ"`
    in a scratch directory containing no lexical-sets.edn on disk
  Then it prints the same EDN vector (e.g. the NURSE entry) that running
    the equivalent query from the source checkout prints, and exits 0 —
    proving the read path falls back to the copy bundled inside the jar

Scenario: a tagged GitHub Release carries the jar as a downloadable asset
  Given target/nemo-words.jar has been built and smoke-tested per the
    scenarios above
  When a release is published with `gh release create <tag>
    target/nemo-words.jar ...`
  Then the release's assets list includes the jar, and
    `gh release download <tag>` from a clean directory retrieves a jar
    that runs identically to the one tested above

Scenario: README documents the download-and-run flow
  Given README.md
  When a user with no Clojure CLI installed reads it
  Then they can find a section explaining the JVM prerequisite, the
    Releases page download link, and the `java -jar nemo-words.jar
    <subcommand>` invocation form, without needing to read any other doc
```

## Follow-up (out of scope here, tracked separately)
- `build-set`/`populate-lexical-sets` still write to the literal disk
  path `resources/lexical-sets.edn` and will fail with a
  `FileNotFoundException` when run from a packaged jar in a directory
  without that path (there is no way to write back into the jar itself).
  Fixing that would mean picking a real writable default outside the
  jar (e.g. an XDG config/cache dir) — a separate, larger design
  decision left for its own story if a downloaded-jar user ever needs to
  rebuild lexical sets rather than just query the ones already bundled.

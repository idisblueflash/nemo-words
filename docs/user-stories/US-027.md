# US-027. Search GA words by onset/nucleus/coda, with graceful fallback

## Background

[ADR-0003](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md)
settled nucleus matching onto raw ARPABET/MRPA tokens, and `ipa.clj`'s
`arpabet-vowels` already finds a GA cell's vowels unambiguously. But
nothing splits a GA cell's ARPABET token string into per-syllable
onset/nucleus/coda — the existing syllable code (`pairs.clj`,
`match.clj`, `rime.clj`) operates on translated IPA text with dot
boundaries, not raw ARPABET tokens (which carry stress digits but no
syllable markers).

Splitting requires deciding how a medial consonant cluster divides
between the previous syllable's coda and the next one's onset. The
Maximal Onset Principle (longest legal word-initial cluster becomes the
onset) handles most cluster shapes. `_david`'s investigation
(3,774 candidate words across 22 cluster shapes, cross-referenced
against `kaikki-en.jsonl`'s orthographic `hyphenations` field where
available — 377 words) found 5 shapes MOP + a whitelist can't settle
reliably: `S T R` (majority splits `s.tr`, opposite of `S K R`'s
`.scr`), `N D R` (near coin-flip), and `N CH`/`K S T`/`N S P` (the
orthographic proxy itself breaks down for these — yod-coalescence,
single-letter digraphs, prefix-dominated samples). Decision: those five
shapes get a manually curated per-word override table
(`resources/data/syllable-overrides.edn`, sourced from a real
pronouncing dictionary, hand-entered); every other shape uses the
algorithmic MOP + `legal-onsets` path. `S T R` itself stays in
`legal-onsets` as the algorithmic default, correctable per-word via
overrides.

Search then needs graceful fallback: a query for a full syllable
(`{:onset :nucleus :coda}`) should prefer an exact match, but degrade
predictably when nothing matches all three. Nucleus is never dropped
(ADR-0003 treats it as load-bearing); coda drops before onset (onset is
more perceptually salient):

1. onset + nucleus + coda
2. onset + nucleus (coda dropped)
3. nucleus + coda (onset dropped)
4. nucleus alone

Each tier tried in order; the first tier with any matches wins.

Full data behind the "5 shapes MOP can't settle" claim above (per-shape
split counts, sample words, why the orthographic proxy breaks down) is
in [US-027-investigation.md](US-027-investigation.md), by `_david`.

## Protocol

- `ipa.clj`: expose `arpabet-vowels` (or an `arpabet-vowel-base?`
  predicate) publicly so `syllable.clj` can reuse it.
- New `nemo_words/syllable.clj` (ns `nemo-words.syllable`):
  - `legal-onsets`: static table of legal English word-initial ARPABET
    consonant sequences (`["S" "T" "R"]`, `["T" "R"]`, `["D" "R"]`,
    `["S" "P" "L"]`, etc.) — the algorithmic default for every shape,
    including the five overridden per-word by `syllable-overrides`.
  - `syllabify`: one GA cell's raw token string (space-separated,
    comma-joined variants) -> per variant, an ordered seq of
    `{:onset :nucleus :coda}` maps (space-joined strings, `""` when
    empty). Vowel positions via `arpabet-vowels`; leading consonants ->
    first syllable's onset; trailing consonants -> last syllable's coda;
    for each internal cluster, its longest suffix present in
    `legal-onsets` becomes the next syllable's onset, the remaining
    prefix becomes the previous syllable's coda.
    Example: `(syllabify "R IH0 S T R EY1 N T")` =>
    `[{:onset "R" :nucleus "IH0" :coda ""} {:onset "S T R" :nucleus "EY1" :coda "N T"}]`
  - New `resources/data/syllable-overrides.edn`: hand-curated
    `{"word" [{:onset :nucleus :coda} ...]}`, scoped to `ga_rp.tsv`
    words containing `N D R`, `S T R`, `N CH`, `K S T`, or `N S P`,
    sourced by hand from a real pronouncing dictionary (not kaikki's
    orthographic proxy). Ships with a handful of seed entries (e.g.
    `"hundred"`); everything else starts as `{}` (expected, not a bug).
  - `row-syllables`: dict row (`{:word :ga-tokens :rp-tokens}`) -> the
    flattened syllable seq: use `syllable-overrides` directly if the
    lowercased word has an entry (skip the algorithm entirely);
    otherwise flatten `syllabify` across every comma-joined GA variant.
  - `syllable-matches?`: one syllable map + a query map (any subset of
    `:onset :nucleus :coda`, each converted via `ipa/ipa->arpabet` and
    stress-stripped like `ipa.clj`'s existing `:ga` matching) -> true if
    the syllable's value for every present query key *contains*
    (substring) the query's converted value.
  - `search`: dict + query map -> `{:tier ... :rows [...]}`, trying the
    four fallback tiers in order, skipping tiers whose required keys
    aren't in the query (e.g. no `:onset` skips tiers 1-2, starts at
    tier 3); returns the first tier with any matching row (a row matches
    if any of its syllables satisfies `syllable-matches?` for that
    tier), or `{:tier nil :rows []}` if none match.
- `core.clj`: new `syllable-search` CLI subcommand (`--onset --nucleus --coda`, each optional, at least one required), printing which tier
  matched then `word\tGA` per row (reusing `row->ga-display`), wired
  into `-main`'s dispatch.

## Acceptance Criteria

```gherkin
Scenario: syllabify splits a GA cell into onset/nucleus/coda per syllable
  Given the GA token string "R IH0 S T R EY1 N T" (restraint)
  When syllabify is called
  Then it returns two syllables, the second being
    {:onset "S T R" :nucleus "EY1" :coda "N T"}

Scenario: a data-ambiguous cluster uses the algorithmic default absent an override
  Given the GA token string "M IH1 N IH0 S T R IY0" (ministry), a word
    not present in syllable-overrides.edn
  When row-syllables is called for the "ministry" row
  Then it falls back to syllabify's algorithmic "S T R" legal-onsets
    default (S T R stays whole as the onset), even though the Background's
    data shows most sampled S T R words actually split s.tr — this is the
    known, accepted limitation an override entry would correct

Scenario: an overridden word's syllable-overrides.edn entry wins over the algorithm
  Given syllable-overrides.edn contains an entry for "hundred" with an
    explicit {:onset "R" :nucleus "EH1" :coda "ND"} / {:onset "R" :nucleus "AH0" :coda "D"}
    (or equivalent nd.r) split
  When row-syllables is called for the "hundred" row
  Then it returns exactly the override's syllables, without running
    syllabify's algorithmic legal-onsets matching for that word

Scenario: full onset+nucleus+coda query matches when the whole syllable exists
  Given a dict containing "restraint" with a syllable
    {:onset "str" :nucleus "eɪ" :coda "nt"}
  When search is called with {:onset "str" :nucleus "eɪ" :coda "nt"}
  Then :tier is :onset+nucleus+coda and the row for "restraint" is included

Scenario: coda is dropped before onset when the full syllable has no match
  Given no dict row has a syllable matching both :onset "str" and :coda "nt"
    together with :nucleus "eɪ", but at least one row has a syllable
    matching :onset "str" and :nucleus "eɪ" alone
  When search is called with {:onset "str" :nucleus "eɪ" :coda "nt"}
  Then :tier is :onset+nucleus (not :nucleus+coda), even though some
    other row might separately satisfy :nucleus "eɪ" + :coda "nt"

Scenario: falls back to nucleus+coda when no onset+nucleus match exists either
  Given no dict row has a syllable matching :onset "str" with :nucleus "eɪ"
    (with or without :coda), but at least one row has a syllable matching
    :nucleus "eɪ" and :coda "nt"
  When search is called with {:onset "str" :nucleus "eɪ" :coda "nt"}
  Then :tier is :nucleus+coda

Scenario: falls back to nucleus alone as the last resort
  Given no dict row has a syllable matching :nucleus "eɪ" combined with
    either :onset "str" or :coda "nt"
  When search is called with {:onset "str" :nucleus "eɪ" :coda "nt"}
  Then :tier is :nucleus and every returned row has at least one syllable
    whose :nucleus contains "eɪ"

Scenario: a query missing onset or coda skips the tiers that need it
  Given a query of {:nucleus "eɪ" :coda "nt"} (no :onset)
  When search is called
  Then the first tier attempted is :nucleus+coda, never :onset+nucleus+coda
    or :onset+nucleus

Scenario: no match at any tier returns an empty result, not an error
  Given no dict row has any syllable whose :nucleus contains the query's
    :nucleus value at all
  When search is called
  Then it returns {:tier nil :rows []}

Scenario: the CLI subcommand prints the matched tier and results
  Given the dict loaded via ipa/load-ga-rp-dict
  When core.clj's syllable-search subcommand is invoked with
    "--onset" "str" "--nucleus" "eɪ" "--coda" "nt"
  Then it prints which tier matched, then one "word\tGA" line per row,
    and returns exit code 0
```

## Follow-up (out of scope here, tracked separately)

- `syllable-overrides.edn` ships with only seed entries. Fully
  populating it for every `ga_rp.tsv` word with `N D R`, `S T R`, `N CH`,
  `K S T`, or `N S P` requires manually checking each word's real
  syllable boundary against a proper pronouncing dictionary — that's the
  user's lookup work to do, not something to derive algorithmically;
  `syllabify`'s algorithmic default stays in place meanwhile, a known,
  accepted gap.
- `legal-onsets` intentionally includes both `S T R` and `S K R` despite
  them behaving oppositely in medial position (see Background) — worth a
  code comment so a future reader doesn't "fix" it into consistency.
- RP-side syllable search (mirroring this story's GA-only scope) is a
  possible follow-on; not required since ADR-0003 already scoped
  nucleus/syllable matching to GA-first.
- `match.clj`/`rime.clj`'s IPA-text-based syllable code is not migrated
  to this token-based `syllable.clj` by this story — separate,
  explicitly out-of-scope cleanup if the two representations ever need
  to converge.

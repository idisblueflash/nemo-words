# US-015. CLI to populate the initial Lexical Sets
As an engineer, I want a real CLI subcommand that runs [US-004](US-004.md)'s `build-set` for all 26 Wells Lexical Sets in one shot, so a fresh checkout can bootstrap `lexical-sets.edn` without a REPL.

## background
[FEAT-001](FEAT-001.md)'s ordering notes deliberately scoped [US-004](US-004.md) as in-process/REPL-only ("Only [US-001](US-001.md), [US-003](US-003.md) and [US-005](US-005.md) also get a thin CLI wrapper... [US-004](US-004.md) and [US-006](US-006.md) are the two composition stories, wiring the finished functions together in-process"). That's fine for building or fixing *one* set at a time, but bootstrapping the initial table means calling `build-set` 26 times with FEAT-001's markdown table's data already in hand — tedious and error-prone to do by hand in a REPL, and not reproducible for a teammate setting up the project fresh. This story adds a thin, real CLI surface over the existing `build-set` function, plus a batch entry point that owns a frozen copy of the 26-row seed table so populating (or re-populating, after a dict update) is one shell command.

`lexical-sets.edn` stays a **local, regenerable build artifact**, not checked-in data (`.gitignore` now covers `resources/lexical-sets.edn`, same treatment as `/target`/`/classes`): every environment (a fresh clone, CI) runs `populate-lexical-sets` once to produce it locally, the same way `resources/data/kaikki-en.jsonl` is fetched rather than committed. This keeps [US-005](US-005.md)'s existing "lexical-sets.edn does not exist yet" test valid against the real default path (`resources/lexical-sets.edn`) without needing a fake missing-path fixture.

Two new `core.clj` subcommands, both thin wrappers with no new business logic:

- `build-set <keyword> <rp> <ga> <word> [<word> ...]` — CLI-exposes the existing `nemo-words.build-set/build-set` for ad hoc single-set (re)builds, e.g. after correcting one row's seed words.
- `populate-lexical-sets` (no args) — iterates `nemo-words.build-set/lexical-sets-table` (the 26 `[keyword rp ga words]` tuples lifted from FEAT-001's table) and calls `build-set` once per row via the new `nemo-words.build-set/populate-lexical-sets` function, upserting/saving into the same `lexical-sets.edn` each time (last row wins on any accidental keyword collision — there are none among the 26).

Both print one `KEYWORD\tkept N/M\tdropped: [...]` summary line per set — `kept`/`dropped` straight from `build-set`'s own filtering (a word drops when it no longer `word-matches?` its set's rp/ga in the current dict), so a caller can see at a glance which seed words didn't survive verification without re-reading the saved file. Re-running either subcommand is safe: `build-set`'s upsert is already idempotent per [US-004](US-004.md)/[US-011](US-011.md).

**A real, encountered data quirk fixed while building the seed table**: FEAT-001's markdown table writes the 7 rhotic rows' GA column (NURSE, NEAR, SQUARE, START, NORTH, FORCE, CURE) with plain ASCII `r` (e.g. `ɑr`), but `en_US_RP_ipa.tsv` only ever stores the IPA turned-r `ɹ` (e.g. `far` → `/fɑɹ/`) — `lettER`'s row in the same table already correctly used `ɹ`, so this was an inconsistency within FEAT-001's own table, not a new decision. `lexical-sets-table` uses `ɹ` for all 8 rhotic rows to match the real dict. Some seed words in those rows still drop after that fix (e.g. `hurt` → dict GA `/hɝt/`, a composed r-colored vowel, not `ɜɹ`) — that's the same, already-documented "dict alternates between a composed r-colored vowel and the decomposed vowel+ɹ sequence for the same sound" limitation [FEAT-001](FEAT-001.md) calls out for lettER's `ɚ` vs `əɹ`, just recurring in other rhotic sets too. Fixing that OR-query gap is out of scope here (FEAT-001 flags it as "not yet specified anywhere"); words that hit it are expected, correctly-reported drops, not a build-set bug.

## Protocol
`nemo-words.build-set/lexical-sets-table` — `[]`, a frozen vector of `[keyword rp ga words]` tuples, one per Wells set, `rp`/`ga` in the raw substring style `build-set` expects (no enclosing slashes).
`nemo-words.build-set/populate-lexical-sets` — `dict (+ optional path) -> ({:keyword :kept :dropped} ...)`, one summary map per row in table order, after upserting/saving all 26 into `lexical-sets.edn`.
`nemo-words.core/build-set-cli` / `nemo-words.core/populate-lexical-sets-cli` — thin CLI wrappers, dispatched from `-main` as the `build-set` / `populate-lexical-sets` subcommands.

## Acceptance Criteria

```gherkin
Scenario: Populate every Wells set from a clean slate
  Given lexical-sets.edn does not exist yet
  When I run `clojure -M -m nemo-words.core populate-lexical-sets`
  Then lexical-sets.edn is created with one entry per keyword in nemo-words.build-set/lexical-sets-table
  And each entry's :rp/:ga match that row's seed rp/ga
  And each entry's :words is exactly that row's seed words filtered down to only those that still word-matches? the current dict
  And stdout has one "KEYWORD\tkept N/M..." summary line per set, in table order
  And the process exits 0

Scenario: Re-running populate-lexical-sets is idempotent
  Given lexical-sets.edn already has all 26 sets from a prior run
  When I run populate-lexical-sets again with the same dict
  Then every entry is replaced with the same content (no duplicates, no drift)
  And every entry not in lexical-sets-table (none, today) would be left untouched

Scenario: Ad hoc single-set build via the build-set subcommand
  Given a keyword, rp, ga, and a list of seed words as CLI args
  When I run `clojure -M -m nemo-words.core build-set nurse ɜː ɜɹ hurt lurk urge burst jerk term`
  Then lexical-sets.edn gains/updates a "nurse" entry with the words that still match ɜː/ɜɹ in the current dict
  And stdout prints one "nurse\tkept N/6..." summary line
  And the process exits 0

Scenario: A seed word no longer matches the current dict
  Given one seed word in a row no longer word-matches? that row's rp/ga (e.g. the dict changed)
  When that row is built (via either subcommand)
  Then that word is dropped from the saved :words
  And it's listed in that row's "dropped: [...]" summary
  And no error is raised
```

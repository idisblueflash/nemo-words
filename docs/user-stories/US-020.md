# US-020. Bidirectional ARPABET ↔ IPA conversion

Part of [FEAT-002](FEAT-002.md) (split for parallel implementation — see that
feature for the full background). Independent of [US-017](US-017.md)/[US-018](US-018.md)/
[US-019](US-019.md)/[US-021](US-021.md) — pure conversion functions, no file I/O, no brand
parsing. Can be built in parallel with all of them.

As an engineer, I want the existing forward `arpabet->ipa` reused as-is
plus a new reverse `ipa->arpabet`, so [US-019](US-019.md)'s display path has
tokens→IPA (already available) and a future consumer (e.g. translating
the Lexical Sets Table's IPA-authored targets into ARPABET nucleus
tokens, so nucleus matching can stay token-to-token per
[0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md) instead of decomposing
IPA per word) has IPA→tokens too.

## background
`arpabet->ipa` and the `arpabet-phoneme->ipa` map already exist in
`nemo-words.ipa` (used today by the `:cmudict` brand for the live
four-source lookup tool) — this story does **not** rebuild that
direction, only reuses it and adds string-level cell wrapping
(`ga-tokens->ipa`, handling comma-joined multi-variant cells, needed by
[US-019](US-019.md)'s display path).

The reverse direction, `ipa->arpabet`, is new and harder than the
forward one: ARPABET tokens are space-separated and self-delimiting
(`K AE1 T`), but IPA is a continuous string with multi-codepoint symbols
(`tʃ`, `dʒ`, `aʊ`, `aɪ`, `eɪ`, `ɔɪ`, `oʊ`) and a stress mark (`ˈ`/`ˌ`)
that precedes — rather than attaches to — its vowel. Reconstructing
tokens requires a greedy-longest-match tokenizer over
`arpabet-phoneme->ipa`'s values (checking multi-character IPA symbols
before single-character ones) plus re-attaching any preceding stress
mark as a trailing digit (`1`/`2`) on the vowel token that follows it,
`0` (or the special `AH0`→`ə`/`ER0`→`ɚ` cases in reverse) when no mark
precedes a vowel.

**Known limitation, accepted**: ARPABET's `AH0` (unstressed schwa) and
similar many-to-one collapses mean `ipa->arpabet` is a best-effort
reconstruction, not guaranteed round-trip-exact for every possible IPA
string, only for strings that were themselves produced by (or are
consistent with) `arpabet->ipa`'s output conventions. Round-tripping
arbitrary externally-authored IPA (e.g. a different source's stylistic
choices) is out of scope.

## Protocol
- `ga-tokens->ipa` [cell-string → IPA-string]: split a raw GA cell on
  `,` (multi-variant), split each variant on whitespace into ARPABET
  tokens, run each through the existing `arpabet->ipa`, rejoin variants
  with `,`. This is the function [US-019](US-019.md)'s display path calls.
- `ipa->arpabet` [IPA-string → ARPABET-token-vector]: tokenize the IPA
  string greedily against `arpabet-phoneme->ipa`'s value set (longest
  match first, to correctly split e.g. `tʃ` before falling back to `t`),
  tracking any `ˈ`/`ˌ` immediately preceding a vowel and re-encoding it
  as that vowel token's trailing digit (`1`/`2`); vowels with no
  preceding mark get `0`.

## Acceptance Criteria

```gherkin
Scenario: ga-tokens->ipa wraps the existing arpabet->ipa for a single variant
  Given the raw GA cell "K AA1 R"
  When ga-tokens->ipa is called on it
  Then the result is "kˈɑɹ", the same output arpabet->ipa already produces
    for ["K" "AA1" "R"]

Scenario: ga-tokens->ipa handles comma-joined multi-variant cells
  Given the raw GA cell "R IY1 D,R EH1 D"
  When ga-tokens->ipa is called on it
  Then the result is "ɹˈid,ɹˈɛd"

Scenario: ipa->arpabet reconstructs a simple word's tokens
  Given the IPA string "kˈæt"
  When ipa->arpabet is called on it
  Then the result is ["K" "AE1" "T"]

Scenario: ipa->arpabet handles multi-codepoint IPA symbols
  Given the IPA string "tʃˈɛs"
  When ipa->arpabet is called on it
  Then the result starts with "CH" "EH1", not a mis-split single-character read of "t" "ʃ"

Scenario: ipa->arpabet handles an unstressed vowel with no preceding mark
  Given the IPA string "əˈbʌv"
  When ipa->arpabet is called on it
  Then the unstressed leading vowel token is "AH0" (or the schwa-equivalent
    zero-stress form), not missing a digit entirely

Scenario: round-trip consistency for arpabet->ipa's own output
  Given any ARPABET token vector v
  When v is converted via arpabet->ipa then the result is converted back via ipa->arpabet
  Then the round-tripped token vector equals v
```

## Follow-up
`ipa->arpabet` has no consumer wired up yet — it exists for a future
story (translating the Lexical Sets Table's IPA targets into ARPABET
nucleus tokens for [0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md)-
style matching), tracked separately once that need is concretely scoped.

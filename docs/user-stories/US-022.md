# US-022. Migrate `lookup-rows`/`word-matches?` to token-based matching

Part of [FEAT-002](FEAT-002.md) (split for parallel implementation — see that
feature for the full background). **Depends on [US-019](US-019.md), [US-020](US-020.md),
and [US-021](US-021.md) all landing first** — this story's queries convert IPA to
tokens via US-020/US-021's reverse-conversion functions, and match
against the `:ga-tokens`/`:rp-tokens` shape [US-019](US-019.md)'s renamed loader
produces.

As an engineer, I want `lookup-rows`/`word-matches?` (and everything
built on them: `populate-lexical-sets`, `core.clj`'s `ipa-lookup` and
`populate-lexical-sets-cli` subcommands, `extend_set.clj`, `match.clj`,
`rime.clj`) to keep working against the dictionary [US-019](US-019.md) produces,
matching per
[0003-match-nucleus-against-arpabet-mrpa-tokens](../decisions/0003-match-nucleus-against-arpabet-mrpa-tokens.md)'s decision (raw
phoneme tokens, no ligature decomposition) instead of the old IPA-
substring approach — **without breaking any existing caller's query
signature**, since [US-001](US-001.md)/[US-004](US-004.md)/[US-005](US-005.md)/[US-006](US-006.md)/[US-014](US-014.md)
already shipped against IPA-string queries.

## background
This is not optional cleanup — it's the piece that makes [US-019](US-019.md)
shippable without breaking the build. Once `load-rp-ga-dict` is renamed
`load-ga-rp-dict` and returns `{:word :ga-tokens :rp-tokens}` (raw
phoneme tokens, per US-019) instead of `{:word :rp :ga}` (IPA), every
current caller of `lookup-rows`/`word-matches?` breaks: they pass IPA
strings (e.g. `/kɑː/`) as query params and expect to match against IPA
cell text that no longer exists in the row shape.

The fix is not to change what callers pass in — every existing caller
(`build_set.clj`'s `populate-lexical-sets`, `core.clj`'s `ipa-lookup` CLI
subcommand, `extend_set.clj`, `match.clj`, `rime.clj`) was built and
tested against IPA-string queries, and re-authoring all of their call
sites to pass raw tokens instead would be a much larger, riskier change
than this story needs to be. Instead, `lookup-rows`/`word-matches?` keep
their external signature (`:rp ipa-string` / `:ga ipa-string` / etc.) but
change their *internal* matching: convert the incoming IPA query to raw
tokens via [US-020](US-020.md)'s `ipa->arpabet` (for `:ga`) / [US-021](US-021.md)'s
`ipa->mrpa` (for `:rp`), then match the resulting token string as a
substring of the row's `:ga-tokens`/`:rp-tokens` field — no ligature
decomposition needed, because the comparison happens entirely in token
space per ADR-0003, on both sides.

## Protocol
- `lookup-rows` opts (`:rp`, `:ga`, `:pair`, `:pair-substring`) keep
  accepting IPA strings exactly as before — no caller-side changes
  needed anywhere in `build_set.clj`, `core.clj`, `extend_set.clj`,
  `match.clj`, or `rime.clj`.
- Internally, each IPA query value is converted once via `ipa->arpabet`
  (GA side) or `ipa->mrpa` (RP side), joined into a space-separated
  token string the same way the stored `:ga-tokens`/`:rp-tokens` fields
  are, then matched as a substring against the corresponding field —
  replacing the current direct IPA-text substring match.
- `:word` and exact-match opts (`:pair`) work unchanged in spirit:
  `:word` still matches on `:word` directly (untouched by this change);
  `:pair` becomes an exact match on the converted token strings instead
  of exact IPA text.
- `word-matches?` (used by `populate-lexical-sets`/`build_set.clj`)
  needs no signature change — it already just calls `lookup-rows`
  internally and inherits the new matching behavior.
- `core.clj`'s `populate-lexical-sets-cli` and `ipa-lookup` subcommand
  switch their `(ipa/load-rp-ga-dict)` call to `(ipa/load-ga-rp-dict)` —
  the only required call-site edit in this story, since the function
  itself was renamed by [US-019](US-019.md).

## Acceptance Criteria

```gherkin
Scenario: an IPA :ga query still matches, now via token conversion internally
  Given a dict row {:word "car" :ga-tokens "K AA1 R" :rp-tokens "k aa"}
  When lookup-rows is called with {:ga "/ɑɹ/"}
  Then the row for "car" is returned, same as the old IPA-substring behavior

Scenario: an IPA :rp query still matches against BEEP's non-rhotic tokens
  Given a dict row {:word "care" :ga-tokens "K EH1 R" :rp-tokens "k ea"}
  When lookup-rows is called with {:rp "ɛə"}
  Then the row for "care" is returned

Scenario: word-matches? keeps working for populate-lexical-sets unchanged
  Given the dict loaded via load-ga-rp-dict, and lexical-sets.edn's NURSE
    row targets rp "ɜː" ga "ɜɹ"
  When word-matches? is called on a NURSE-set candidate word
  Then it returns true/false consistent with the pre-migration IPA-substring
    result for the same word, dict, and targets

Scenario: core.clj's CLI subcommands use the renamed loader
  Given the populate-lexical-sets or ipa-lookup subcommand is invoked
  When it loads the dictionary
  Then it calls nemo-words.ipa/load-ga-rp-dict, not the now-removed load-rp-ga-dict

Scenario: no ligature-decomposition step remains in the matching path
  Given a query IPA string containing a rhotic ligature (e.g. "ɝ" or "ɚ")
  When lookup-rows converts it via ipa->arpabet/ipa->mrpa and matches
  Then the match happens purely by token-string comparison, with no
    separate ligature-normalization step in lookup-rows itself
```
